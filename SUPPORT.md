Support

This document explains where to request help with Sssssssddddd projects.

Before Asking for Help

Please check:

1. The repository README.
2. Project documentation.
3. Existing issues and discussions.
4. Installation and configuration instructions.
5. Known limitations and troubleshooting documentation.

Include enough technical context for another person to reproduce the problem.

Bug Reports

Use the project’s issue tracker for reproducible bugs when the repository provides one.

A useful bug report should include:

* A concise description.
* Expected behavior.
* Actual behavior.
* Steps to reproduce.
* Relevant environment information.
* Error messages or logs.
* A minimal reproduction when practical.

Remove secrets and unnecessary personal information before posting logs.

Feature Requests

Feature requests should explain the problem being solved, intended users or workflow, proposed behavior, important constraints, and alternatives considered when relevant.

Security Issues

Do not report security vulnerabilities through public issues. Follow SECURITY.md for private security reporting.

Project-Specific Support

Individual repositories may provide additional support channels or procedures. Follow those instructions when they are more specific than this document.

What Support Does Not Guarantee

Open-source or experimental projects may have limited support availability. A support request does not guarantee a specific response time, acceptance of a feature request, immediate bug fixes, or compatibility with unsupported environments.

Good Support Requests

Good support requests are specific, reproducible, respectful, based on available documentation, and free of secrets and unnecessary private information.
